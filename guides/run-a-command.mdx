---
title: Run a command
description: Choose between buffered exec, TTY exec, and managed sessions
---

There are three distinct ways to run a command in a sandbox. This guide covers when to reach for each and shows a REST, CLI, and SDK example per mode. For field-level detail on request/response shapes, see [Exec](/concepts/exec) and [Sessions](/concepts/sessions) — this page doesn't repeat those.

| Mode | Endpoint | Use it when |
| --- | --- | --- |
| Buffered exec | `POST /v1/sandbox/{sandbox_id}/exec` | You want one command's exit code and output as a single JSON response. |
| TTY exec | `GET /v1/sandbox/{sandbox_id}/exec` (WebSocket) | You want an interactive, transient terminal for one command. |
| Managed sessions | `POST /v1/sandbox/{sandbox_id}/sessions` | You want a named command you can list, re-attach to, or kill independently of the connection that started it. |

All three assume you already have a running `sandbox_id` — see the [Quickstart](/quickstart) if you don't yet.

## Buffered exec

The default choice for scripts, CI, and anything where you just want a result. Synchronous, JSON in and out, no WebSocket. A non-zero `exit_code` is still a `200` — check the body, not the HTTP status, to determine command success.

<CodeGroup>
```shell cURL
curl -s -X POST "https://api.tyto.run/v1/sandbox/$SANDBOX_ID/exec" \
  -H "Authorization: Bearer $BONYA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"cmd": ["bash", "-lc", "echo hi"], "timeout_s": 30}'
```

```shell CLI
tyto exec $SANDBOX_ID -- bash -lc 'echo hi'
```

```ts TypeScript
const result = await sandbox.exec(["bash", "-lc", "echo hi"], { timeout: 30 });
console.log(result.stdout, result.exitCode, result.ok);
```

```python Python
result = sandbox.exec(["bash", "-lc", "echo hi"], timeout=30)
print(result.stdout, result.exit_code, result.ok)
```
</CodeGroup>

Use `check: true` (TypeScript/Go) or `check=True` (Python) to raise/throw on a non-ok result instead of inspecting `exit_code` yourself.

For output too large to buffer, a command that runs longer than you want to wait synchronously, or stdin you need to stream interactively, use the SDK's streaming exec (`execStream()`/`exec_stream()`/`ExecStream`) instead of buffered — see [Usage](/sdks/typescript/usage#streaming-exec) for that variant. It's still one-shot: the remote process ends when the stream closes, same as buffered exec, just not blocked on a single JSON response.

## TTY exec

An HTTP upgrade to a WebSocket for a transient, interactive terminal — one-off, not tracked as a named session. This is what you want for a human typing at a live shell. See [Exec](/concepts/exec#tty-exec) and [WebSockets](/concepts/websockets) for the upgrade and START-frame mechanics; they aren't repeated here.

<CodeGroup>
```shell cURL
# WebSocket upgrade — shown with websocat, not curl, since curl can't
# speak the protocol after the 101 response.
websocat "wss://api.tyto.run/v1/sandbox/$SANDBOX_ID/exec" \
  -H "Authorization: Bearer $BONYA_API_KEY"
# then send a TTYStartRequest as the START frame
```

```shell CLI
tyto console $SANDBOX_ID
```

```ts TypeScript
const session = sandbox.execStream(["bash"], { tty: true, cols: 100, rows: 30 });
for await (const event of session) {
  // Stdout, Stderr, Exit events; TTY mode merges stderr into stdout
}
```
</CodeGroup>

The CLI's `tyto console` is the everyday entry point for this — it's a shortcut for attaching to (or creating) a managed session named `console`, so under the hood it actually goes through the managed-session path below rather than raw TTY exec. Reach for raw TTY exec directly from an SDK when you want an interactive terminal without the persistence a named session implies.

## Managed sessions

For a command that should keep running after you disconnect — a dev server, a long build — and that you want to list, re-attach to, or kill independently of any single connection, use a managed session. Sessions are named, tracked server-side, and survive the sandbox suspending and resuming. See [Sessions](/concepts/sessions) for the full field reference.

<CodeGroup>
```shell cURL
# create
curl -s -X POST "https://api.tyto.run/v1/sandbox/$SANDBOX_ID/sessions" \
  -H "Authorization: Bearer $BONYA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "dev", "cmd": ["npm", "run", "dev"]}'

# list
curl -s "https://api.tyto.run/v1/sandbox/$SANDBOX_ID/sessions" \
  -H "Authorization: Bearer $BONYA_API_KEY"

# kill
curl -s -X POST "https://api.tyto.run/v1/sandbox/$SANDBOX_ID/sessions/dev/kill" \
  -H "Authorization: Bearer $BONYA_API_KEY"
```

```shell CLI
tyto session create $SANDBOX_ID dev -- npm run dev
tyto session list $SANDBOX_ID
tyto session attach $SANDBOX_ID dev
tyto session kill $SANDBOX_ID dev
```

```python Python
info = sandbox.sessions.create("dev", ["npm", "run", "dev"])

session = sandbox.sessions.attach("dev")
for event in session:
    ...
session.detach()

for info in sandbox.sessions.list():
    print(info.name, info.status)

sandbox.sessions.kill("dev")
```
</CodeGroup>

Attaching to a session is also a WebSocket upgrade (`GET .../sessions/{session_name}/attach`) — multiple clients can attach to the same session, and a new attach preempts whoever was attached before. Listing sessions never wakes a suspended sandbox; it answers from the state captured at suspend time.
