---
title: Sessions
description: Long-lived, named command sessions inside a sandbox
---

A **session** is a managed, named command running inside a sandbox — distinct from a one-shot [exec](/concepts/exec) call. Sessions are tracked server-side by name, so you can list them, attach to their output, and kill them independently of the connection that created them.

<Note>
Sessions are one of three ways to run commands in a sandbox. For a synchronous, buffered command or an unnamed interactive TTY, see [Exec](/concepts/exec).
</Note>

## Identity

A session is scoped to a `sandbox_id` and keyed by `session_name`, which must match `^[a-z][a-z0-9-]{0,31}$` — lowercase, starting with a letter, up to 32 characters. There's no separate session ID; the name is the identifier within its sandbox.

## Creating a session

```
POST /v1/sandbox/{sandbox_id}/sessions
```

The request body extends the common command shape (`cmd`, `env`, `path`) with session-specific fields:

<ParamField body="name" type="string" required>
  Session name. Must match `^[a-z][a-z0-9-]{0,31}$`.
</ParamField>
<ParamField body="cmd" type="string[]" required>
  Argv to run. At least one element.
</ParamField>
<ParamField body="env" type="object">
  Environment variables to set.
</ParamField>
<ParamField body="path" type="string">
  Working directory.
</ParamField>
<ParamField body="cols" type="integer">
  Terminal width, 1–512.
</ParamField>
<ParamField body="rows" type="integer">
  Terminal height, 1–512.
</ParamField>
<ParamField body="replace" type="boolean" default="false">
  Whether to replace an existing session of the same name.
</ParamField>

A successful create returns `201` with `{ "session": { ...SessionInfo } }`.

### Name collisions

<Warning>
Creating a session whose name collides with a **live** (non-terminal) session returns `409 session_exists`. `replace: true` only takes effect against a session that has already reached a terminal state (`EXITED`, `KILLED`, or `FAILED`) — it does not let you forcibly replace a session that's still running or attached. To replace a running session, kill it first, then create.
</Warning>

## Session state

Each `SessionInfo` reports:

<ResponseField name="name" type="string" required>
  The session name.
</ResponseField>
<ResponseField name="command" type="string[]" required>
  The argv the session was started with.
</ResponseField>
<ResponseField name="working_dir" type="string" required>
  The session's working directory.
</ResponseField>
<ResponseField name="status" type="string" required>
  One of `UNSPECIFIED`, `STARTING`, `IDLE`, `ATTACHED`, `EXITED`, `KILLED`, `FAILED`.
</ResponseField>
<ResponseField name="attached" type="boolean" required>
  Whether a client is currently attached.
</ResponseField>
<ResponseField name="started_at_unix_nanos" type="integer" required>
  Start time.
</ResponseField>
<ResponseField name="last_activity_unix_nanos" type="integer" required>
  Last observed activity.
</ResponseField>
<ResponseField name="ended_at_unix_nanos" type="integer">
  End time, once the session has reached a terminal state.
</ResponseField>
<ResponseField name="exit" type="object">
  `{ exit_code, signaled, signal }`, present once the session has exited.
</ResponseField>

`EXITED`, `KILLED`, and `FAILED` are the terminal states referenced above under name collisions; `STARTING`, `IDLE`, and `ATTACHED` are all live.

## Listing sessions

```
GET /v1/sandbox/{sandbox_id}/sessions
```

Returns `SessionListResponse`:

<ResponseField name="sessions" type="SessionInfo[]" required>
  All sessions tracked for the sandbox.
</ResponseField>
<ResponseField name="sandbox_suspended" type="boolean" required>
  Whether the sandbox was suspended when this list was produced.
</ResponseField>

<Note>
Listing sessions **never wakes** a suspended sandbox. If the sandbox is suspended, the response answers from a snapshot of session state taken at suspend time, and `sandbox_suspended` is `true` — it does not resume the sandbox to get a live answer. To act on the sessions themselves, resume the sandbox first (see [Sandboxes](/concepts/sandboxes)).
</Note>

## Attaching to a session

```
GET /v1/sandbox/{sandbox_id}/sessions/{session_name}/attach
```

This is a WebSocket upgrade — see [WebSockets](/concepts/websockets) for how the upgrade, the START frame (`AttachStartRequest`), and admission work. Multiple clients can attach to the same session.

## Killing a session

```
POST /v1/sandbox/{sandbox_id}/sessions/{session_name}/kill
```

Request body (`SessionKillRequest`, optional):

<ParamField body="signal" type="string" default="TERM">
  One of `TERM`, `KILL`, `INT`, `HUP`.
</ParamField>
<ParamField body="grace_ms" type="integer" default="5000">
  Milliseconds to wait after the signal before the session is considered killed, 0–60000.
</ParamField>

Returns `200` with `{ "session": { ...SessionInfo } }` reflecting the signal having been delivered.
