title: Snapshots
description: Capture a sandbox's disk state via the SDKs and CLI

<Warning>
Snapshots are **not part of the public REST API**. There is no `/v1/sandbox/{sandbox_id}/snapshots` path or any other snapshot route in the OpenAPI contract — snapshot operations exist only as gRPC calls made through the official SDKs and CLI, and won't appear in the [API Reference](/api-reference) tab.
</Warning>

A **snapshot** captures a sandbox's disk state. It's identified by a `snapshot_id` and tied to the `source_sandbox_id` it was taken from.

## Creating a snapshot

The source sandbox must be **running**. A suspended, failed, or already-deleted sandbox is rejected rather than snapshotted.

<CodeGroup>
```python Python
snapshot = sandbox.snapshot()
```

```go Go
snapshot, err := client.CreateSnapshot(ctx, sandbox.ID, tyto.SnapshotOptions{
	IdempotencyKey: "example-snapshot-1",
})
```

```shell CLI
tyto snapshot create web
```
</CodeGroup>

Both SDKs accept an idempotency key for create, so a retried call returns the same snapshot rather than minting a second one.

A `Snapshot` handle carries its `snapshot_id` and the `source_sandbox_id` it came from. Its identity outlives the source sandbox — deleting the sandbox that produced a snapshot is a separate decision from deleting the snapshot itself.

## Deleting a snapshot

<CodeGroup>
```python Python
snapshot.delete()
```

```shell CLI
tyto snapshot delete web <snapshot-id>
```
</CodeGroup>

Delete is idempotent: calling it again on an already-deleted snapshot is a no-op rather than an error.

<Note>
There is no list, restore, or fork operation for snapshots anywhere in the current SDKs or CLI. The CLI's `snapshot` command group has only `create` and `delete` subcommands — track `snapshot_id` values yourself if you need to find a snapshot again later.
</Note>
