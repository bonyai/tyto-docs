## What you can do

| I want to… | Call |
|---|---|
| Start a sandbox | `client.createSandbox({ template })` |
| Reconnect to one | `client.getSandbox(id)` / `.getSandboxByName(name)` |
| Find my sandboxes | `client.listSandboxes()` |
| Run a command | `sandbox.exec(cmd)` |
| Stream output live | `sandbox.execStream(cmd)` |
| Keep a process running after I disconnect | `sandbox.createSession(name, cmd)` |
| Move files in and out | `sandbox.readFile`/`.writeFile`/`.uploadFile`/`.downloadFile` |
| Expose a port to the web | `sandbox.createPreview(port)` |
| Capture disk state | `sandbox.snapshot()` |
| Run a managed one-off or scheduled job | `client.runJob(spec)` / `client.createJobSchedule(...)` |
| See what templates exist | `client.listTemplates()` |

Everything here is a **flat method** directly on `Tyto` or `Sandbox` —
there is no `client.sandboxes.create(...)`-style namespace to navigate.
`client.createSandbox(...)`, `client.getSandbox(id)`,
`client.getSandboxByName(name)`, `client.listSandboxes()`,
`client.deleteSandbox(id)`, `client.resumeSandbox(id)` are the whole
sandbox-lifecycle surface on `Tyto`. Once you're holding a `Sandbox`,
`sandbox.createSession(...)`, `sandbox.createPreview(...)`,
`sandbox.snapshot(...)`, and the file methods below are flat methods on it
directly.

<Note>
`Tyto` also has session/preview convenience methods that take a sandbox id
directly instead of a `Sandbox` — `client.createSession(sandboxId, name,
cmd)`, `client.listSessions(sandboxId)`, `client.createPreview(sandboxId,
port)`, and similar. Each does a `getSandbox()` first and then delegates,
which is one extra round trip compared to already holding a `Sandbox`
handle. Prefer calling directly on `sandbox` when you have one in hand;
reach for a client-level call only when all you have is an id.
</Note>

## Create sandboxes

```ts
import { Tyto, Wait } from "@bonya-ai/tyto";

const client = new Tyto();
const sandbox = await client.createSandbox({
  template: "bonya-dev",
  wait: Wait.READY,
  idempotencyKey: "create-job-123",
});
```

`client.createSandbox(options)` returns a `Promise<Sandbox>`.

| Option | Type | Description |
|---|---|---|
| `template` | `string` | May be omitted to use the deployment's configured default template, if it has one. |
| `version` | `string` | Template version. Server default when omitted. |
| `wait` | `Wait \| "ready" \| "none"` | Defaults to `Wait.READY`. |
| `idempotencyKey` | `string` | Generated and reused for transport retries if omitted. |
| `name` | `string` | Optional display name, at most 80 bytes. Server generates a friendly one when omitted. Names are not unique. |

`Wait.READY` (or `"ready"`) asks the service to return a running sandbox —
`lastObservedStatus === Status.RUNNING`. `Wait.NONE` (or `"none"`) returns
as soon as the service accepts the request — `lastObservedStatus ===
Status.CREATING`.

If create exhausts its deadline, the SDK throws `SandboxCreationTimeoutError`,
which carries the `idempotencyKey` used so you can retry the same creation
rather than starting a second sandbox.

Sandbox fields: `sandbox.id`, `.operationId`, `.template`, `.version`,
`.lastObservedStatus`.

## Get, list, and get by name

```ts
const sandbox = await client.getSandbox("sbx_123");

import { Status } from "@bonya-ai/tyto";

for await (const summary of client.listSandboxes({
  states: [Status.RUNNING, Status.SUSPENDED],
  limit: 20,
})) {
  console.log(summary.id, summary.lastObservedStatus);
}

const byName = await client.getSandboxByName("web-server");
```

`getSandbox(sandboxId)` requires a non-empty id and returns a usable
`Sandbox` handle. It does **not** explicitly resume the sandbox — exec and
filesystem calls are what wake a suspended one.

`listSandboxes(options)` returns an `AsyncIterableIterator<SandboxSummary>`
and pages as you iterate. `limit: 0` yields nothing without an RPC.
`options.name` filters to sandboxes carrying an exact display name (names
aren't unique, so this can still match more than one). Valid `states`
filters are `Status.CREATING`, `RUNNING`, `SUSPENDING`, `SUSPENDED`,
`RESUMING`, and `FAILED` — `Status.DELETED` is not a valid filter. A
`SandboxSummary` has `id`, `operationId`, `template`, `version`,
`lastObservedStatus`, `failureCode`, `failureMessage` — it cannot run
`exec`; call `getSandbox(summary.id)` first.

`getSandboxByName(name)` resolves a display name to a single sandbox.
Names are not unique: if more than one sandbox carries the name, it throws
rather than picking one (a later `delete()` could otherwise destroy the
wrong sandbox). If none match, it throws `SandboxNotFoundError`.

## Delete and cleanup

```ts
const result = await sandbox.delete();
console.log(result.sandboxId, result.alreadyDeleted);
```

`sandbox.delete()` returns `DeleteResult { sandboxId, alreadyDeleted }`.
Calling it again on the same `Sandbox` object is local and idempotent — no
second RPC. There is no automatic cleanup on scope exit; use `try`/`finally`.

## Resume

```ts
const resume = await sandbox.resume({ idempotencyKey: "resume-job-123" });
console.log(resume.sandboxId, resume.lifecycleOperationId, resume.alreadyRunning);
```

`sandbox.resume(options)` returns `ResumeResult { sandboxId,
lifecycleOperationId, alreadyRunning }` and updates the sandbox's private
exec endpoint/capability, setting `lastObservedStatus` to `Status.RUNNING`.
`resume()` on a failed sandbox throws `SandboxFailedError` locally, before
any RPC.

Explicit resume is different from automatic wake: `getSandbox()` never
calls `resume()`, and ordinary exec/filesystem calls don't make a public
`ResumeSandbox` RPC — they hit the sandbox's guest endpoint directly, and
the service may wake it behind that route.

## Exec vs execStream

`exec()` buffers output and resolves once the process exits — good for
short, bounded commands. `execStream()` yields events as they happen —
use it for large output, long-running commands, interactive stdin, or
cancellation. Both are one-shot: the remote process ends when the call (or
stream) ends. This is different from [managed sessions](#managed-console-sessions),
which keep running after you disconnect.

### Buffered exec

```ts
const result = await sandbox.exec(
  ["python3", "-c", "import os; print(os.environ['MODE'])"],
  { env: { MODE: "development" }, cwd: "/workspace", timeout: 10 },
);

console.log(result.stdout, result.stderr, result.exitCode, result.ok);
```

```ts
sandbox.exec(command, {
  env,
  cwd,
  tty,
  cols,
  rows,
  timeout,
  check,
  input,
}): Promise<ExecResult>
```

`command` is either a `string` (run as `["/bin/sh", "-c", command]`) or a
non-empty `readonly string[]` with no empty entries. `env` overlays string
env vars (keys can't contain `=` or NUL). `cwd` sets the remote working
directory. `input` is a `string` or `Uint8Array` written to stdin before
it's half-closed — buffered `input` requires `tty: false`.

`ExecResult` exposes `stdoutBytes`/`stderrBytes` (`Uint8Array`),
`stdout`/`stderr` (UTF-8 getters), `exitCode`, `signaled`, `signal`,
`ok` (`exitCode === 0 && !signaled`), and `toString()` (same as `.stdout`).

`check: true` calls `result.check()` before returning; on a non-ok result
it throws `ExecFailedError`, with the original result at `error.result`.

`exec()` buffers stdout and stderr in client memory. Use `execStream()`
for large output, long-running commands, interactive stdin, or
cancellation.

### Streaming exec

```ts
import { Exit, Stderr, Stdout } from "@bonya-ai/tyto";

const session = sandbox.execStream(["bash", "-lc", "echo out; echo err >&2"]);
try {
  for await (const event of session) {
    if (event instanceof Stdout) process.stdout.write(Buffer.from(event.data));
    else if (event instanceof Stderr) process.stderr.write(Buffer.from(event.data));
    else if (event instanceof Exit) console.log("exit:", event.exitCode);
  }
} finally {
  session.close();
}
```

`execStream(command, { env, cwd, tty, cols, rows, timeout })` returns a
session that is an async iterable of `Stdout`, `Stderr`, and `Exit`
events. Write stdin with `session.write(data: Uint8Array)`, close it with
`session.closeStdin()` (idempotent). `session.cancel()` is idempotent and
sends a cancel frame when possible; `session.close()` cancels an
unfinished session. If iteration reaches the session deadline before the
next event, the SDK cancels the remote exec and throws `TimeoutError`.

### TTY exec

Set `tty: true` for terminal semantics — stdout and stderr share the
terminal stream, so the SDK returns terminal output as `stdout` and leaves
`stderr` empty. Default dimensions are 80x24 (sent on the wire as
`cols: 0, rows: 0`). Provide both `cols` and `rows` together to override —
each must be an integer from 1 through 512, and both require `tty: true`.
Buffered `input` isn't allowed with `tty: true`; use `execStream()` and
`session.write(...)` instead. Resize an active TTY stream with
`session.resize({ cols, rows })`.

## Managed console sessions

Every `Sandbox` has flat methods (`createSession`, `listSessions`,
`killSession`, `attachSession`) for named, persistent command sessions
that **outlive the client connection**. This is the key distinction from
`execStream()`: an exec process dies when its stream closes, but a
managed session keeps running detached, and you can reattach later — even
after the sandbox warm-suspends and resumes — and replay what it produced
while nobody was watching. Use `exec`/`execStream` for one-shot commands;
use managed sessions for long-lived terminals like dev servers you want to
detach from and come back to.

```ts
const info = await sandbox.createSession("server", ["bash"], { cols: 120, rows: 40 });

const session = await sandbox.attachSession("server");
session.write(new TextEncoder().encode("npm run dev\n"));
session.resize({ cols: 140, rows: 45 });
for await (const event of session) {
  // ...
}
session.detach();

const list = await sandbox.listSessions();
for (const info of list) console.log(info.name, info.status);

await sandbox.killSession("server");
```

**Create** — `sandbox.createSession(name, command, { env, cwd, cols, rows, replace })`.
`name` must match `^[a-z][a-z0-9-]{0,31}$`. `command` is a non-empty array
of non-empty strings (no shell-string convenience like `exec()`). Creating
over an existing record throws `SessionExistsError` unless `replace: true`
— and even then, only a terminal record (exited/killed/failed) is
replaced; a running or attached session is never replaced. Returns
`Promise<SessionInfo>`.

**List** — `sandbox.listSessions()` returns a `SessionList`: an immutable,
iterable sequence of `SessionInfo` that also carries `sandboxSuspended:
boolean`. Listing works on a suspended sandbox without waking it.

**Attach** — `sandbox.attachSession(name, { cols, rows, maxReplayBytes })`
returns `Promise<SessionStream>`, resolved once admitted. `session.info`,
`.replayedBytes`, `.historyDropped` describe the bounded replay from while
you were detached (the replay ring is 1 MiB). Attaching preempts any other
attached client — the loser gets `SessionEnded(SessionEndedReason.TAKEOVER)`.
Attaching to a suspended sandbox's session wakes it.

Stream events: `Stdout { data }` (merged output — sessions are TTY-only,
no separate stderr), `Exit { exitCode, signaled, signal }`, `SessionEnded
{ reason }` (`DETACHED` or `TAKEOVER`), `SessionOutputDropped { droppedBytes }`
(client reading too slowly; doesn't end the attach).

`session.write(data)`, `session.resize({ cols, rows })` (1–512 per
dimension), `session.detach()` (ends gracefully, process keeps running),
`session.close()` (calls `detach()` if still open).

**Kill** — `sandbox.killSession(name, { signal, graceMs })` signals the
process group (default `TERM`), escalating to `SIGKILL` after `graceMs`
(default 5000ms). Returns `Promise<SessionInfo>`, but exit info isn't
guaranteed on that response — `kill()` doesn't wait for the guest to reap
the process, so a `listSessions()` shortly after is the reliable way to
see the final exit code. Killing an unknown name throws `SessionNotFoundError`.

`SessionInfo`: `name`, `command`, `workingDir`, `status`, `attached`,
`startedAt`, `lastActivityAt`, `endedAt`, `exit`. `SessionStatus` values:
`UNSPECIFIED`, `STARTING`, `IDLE`, `ATTACHED`, `EXITED`, `KILLED`, `FAILED`.

A session's process never blocks idle suspend by itself. Only an
*attached* stream does, for as long as it stays open; a quiet, detached
session lets the sandbox warm-suspend, and survives the resume with its
process and replay buffer intact — the same session, not a new one.
Output from a detached session still counts as activity and defers idle
suspend while it keeps producing it.

Session calls transparently reissue an expired capability and retry once,
the same way `execStream()` and the file methods below do. Call
`sandbox.reissueCapability()` directly only if you manage tokens yourself.

## Files

File operations are flat methods directly on `Sandbox`:

```ts
await sandbox.writeFile("/workspace/message.txt", "hello\n");
const payload = await sandbox.readFile("/workspace/message.txt");

await sandbox.uploadFile("local-input.bin", "/workspace/input.bin");
await sandbox.downloadFile("/workspace/input.bin", "local-output.bin");

const entries = await sandbox.listFiles("/workspace");
const info = await sandbox.statFile("/workspace/message.txt");

await sandbox.mkdirFile("/workspace/output");
await sandbox.moveFile("/workspace/message.txt", "/workspace/output/message.txt");
await sandbox.removeFile("/workspace/output", true);
```

| Method | Signature |
|---|---|
| `readFile` | `(path: string) => Promise<Uint8Array>` |
| `writeFile` | `(path: string, data: Uint8Array \| string) => Promise<void>` |
| `uploadFile` | `(localPath: string, remotePath: string) => Promise<void>` |
| `downloadFile` | `(remotePath: string, localPath: string) => Promise<void>` |
| `listFiles` | `(path: string) => Promise<FileInfo[]>` |
| `statFile` | `(path: string) => Promise<FileInfo>` |
| `mkdirFile` | `(path: string) => Promise<void>` |
| `removeFile` | `(path: string, recursive?: boolean) => Promise<void>` |
| `moveFile` | `(source: string, destination: string) => Promise<void>` |

`readFile()` buffers the whole file and throws `FilesystemLimitError`
before exceeding `filesystemReadLimit`. `writeFile()` streams in 64 KiB
chunks through a guest-side temp file and publishes atomically; a symlink
at the final path is not followed. `uploadFile()`/`downloadFile()` stream
in 64 KiB chunks; `downloadFile()` uses a temp file, fsync, and atomic
rename. `listFiles()` returns immediate children sorted by name, or
throws — no partial results. `statFile()` returns lstat-style metadata (a
final symlink is reported as a symlink, not followed). `moveFile()` is
same-filesystem, atomic, no-overwrite — cross-filesystem throws
`CrossFilesystemMoveError`, existing destination throws
`RemoteFileExistsError`. `removeFile(path, true)` recurses without
following symlinks and is not atomic.

`FileInfo` is immutable: `path`, `name`, `kind` (`FileKind.FILE` /
`DIRECTORY` / `SYMLINK` / `OTHER`), `size`, `mode`, `modifiedAt`.

## Jobs

A job is a managed run of a command or script — on a new sandbox (created
and, by default, deleted for you) or an existing one. Jobs are how you run
work without holding a `Sandbox` open yourself for the duration.

```ts
const run = await client.runJob({
  newSandbox: { template: "bonya-dev" },
  cmd: ["./run-tests.sh"],
});
console.log(run.status, run.result?.exitCode);
```

`runJob` blocks until the run finishes, bounded by the client's own
timeout — use it for short jobs. `startJob` returns immediately with a
run id instead:

```ts
const { runId } = await client.startJob({
  existingSandboxId: "sbx-123",
  cmd: ["./long-migration.sh"],
});
// ... later ...
const detail = await client.getJobRun(runId);
console.log(detail.status, detail.spec, detail.timeline);
```

`JobSpec` requires exactly one of `existingSandboxId`/`newSandbox`, and
exactly one of `cmd`/`script`. `disposition` (`Disposition.DELETE`, the
default, or `Disposition.KEEP`) controls what happens to a sandbox the job
itself created once the run ends; it's not meaningful for
`existingSandboxId`.

`getJobRun` returns `JobRunDetail`, which adds the stored `spec` and an
activity `timeline` to the run summary `listJobRuns` returns. There is no
endpoint to edit a run in place: to "edit and rerun" one, fetch it with
`getJobRun`, change what you need on its `spec`, and pass that to `runJob`
or `startJob` as a new run.

```ts
for await (const run of client.listJobRuns({ sandboxId: "sbx-123" })) {
  console.log(run.runId, run.status);
}
await client.cancelJobRun(runId); // requests cancellation; cleanup still runs
```

`cancelJobRun` cancels rather than terminates, so the run's own cleanup
(e.g. deleting a sandbox it created) still executes.

## Job schedules

A schedule wraps a `JobSpec` with timing — cron, interval, or a one-shot
future time — so it runs without you calling `runJob` yourself.

```ts
const schedule = await client.createJobSchedule(
  { intervalSeconds: 3600 },
  { newSandbox: { template: "bonya-dev" }, cmd: ["./nightly-report.sh"] },
);
console.log(schedule.scheduleId, schedule.nextRunAtUnixNanos);
```

`ScheduleSpec` requires exactly one of `cronExpressions`, `intervalSeconds`,
and `runAtUnixNanos` (a one-shot: a single future calendar time, refused
if in the past). `overlap` (default `ScheduleOverlap.SKIP`) controls what
a fire does when the previous run from the same schedule is still going.

```ts
for await (const schedule of client.listJobSchedules()) {
  console.log(schedule.scheduleId);
}
const schedule = await client.getJobSchedule(scheduleId);

// updateJobSchedule replaces the whole schedule -- pass every field you
// want to keep, not just the one you're changing.
await client.updateJobSchedule(scheduleId, { intervalSeconds: 7200 }, jobSpec);

await client.setJobSchedulePaused(scheduleId, true, { note: "pausing for maintenance" });
await client.triggerJobSchedule(scheduleId); // fires one run now, ignoring timing
await client.deleteJobSchedule(scheduleId);
```

`JobSchedule.recentRunIds` holds the last 10 fires' run ids (oldest first,
including manual triggers), each a valid `getJobRun` id — so you can
follow a schedule straight to its recent runs without a separate
`listJobRuns` call.

## Templates

```ts
const templates = await client.listTemplates();
for (const template of templates) {
  console.log(template.id, template.version, template.isDefault, template.metadata.os);
}
```

`listTemplates()` lists every `templateId`/version `createSandbox` and
`runJob` will accept, with metadata (OS, installed language stacks, which
AI agent CLIs are preinstalled) to help pick one. Not paginated: the
catalog is the same for every caller. `createSandbox`'s `template` option
may be omitted to use the deployment's configured default template, if it
has one.

## Preview URLs

A preview publishes one guest port at an HTTPS URL a browser can open. The
server must bind a port in 1024–65535; privileged ports are never
previewable, so a guest's ssh can't be handed out by accident.

```ts
const preview = await sandbox.createPreview(3000, { name: "web" });
console.log(preview.url); // https://pv-<26 chars>.preview.tyto.run

await sandbox.listPreviews();
await sandbox.deletePreview(preview.id);
```

A token-mode preview needs the sandbox's capability, and a URL isn't a
safe place to leave one. `sandbox.previewBrowserUrl(preview)` produces a
single-use entry point: the gateway validates the token, trades it for a
host-scoped `HttpOnly` cookie, and redirects without the token in the URL.
It throws on a public preview, which has no token to exchange.

```ts
import { PreviewAuth } from "@bonya-ai/tyto";

const publicPreview = await sandbox.createPreview(8080, { auth: PreviewAuth.PUBLIC });
```

`PreviewAuth.PUBLIC` means anyone with the URL reaches the service, no
credential — the only protection is the 26 random characters in the
hostname, so treat it as published to the internet. `TOKEN` is the
default; an omitted `auth` never yields a public URL.

`createPreview()` returns a fresh capability and the SDK stores it on the
sandbox automatically (the preview scope is newer than a sandbox's
original token). If you're holding a capability elsewhere, refresh it
explicitly with `sandbox.reissueCapability()`.

Traffic to a preview URL wakes a suspended sandbox; the first request
after suspend pays resume latency and may return `503` with `Retry-After`.

### Preview limitations

- **Bind to the interface, not localhost only.** A server listening solely
  on `127.0.0.1` inside the guest is reachable, but one bound to a
  specific non-loopback address may not be. `0.0.0.0` is the reliable
  choice.
- **Server-Sent Events reconnect.** An SSE stream is cut at the 120-second
  request cap since it isn't an HTTP upgrade. `EventSource` reconnects
  automatically; a long-lived stream that must not break should use a
  WebSocket.
- **WebSocket auth is cookie or bearer only.** WebSocket clients don't
  follow redirects, so the token-query-parameter exchange doesn't work for
  them — open a normal page first to obtain the cookie, or send the
  capability as a bearer header.
- **A suspend cuts open connections.** Preview connections deliberately
  don't defer idle-suspend, so an open WebSocket doesn't keep a sandbox
  alive. The next request wakes it.

## Snapshots

<Note>
Snapshots exist only through the SDKs (and the `tyto` CLI) over gRPC —
there is no public REST endpoint for creating or deleting them.
</Note>

```ts
const snapshot = await sandbox.snapshot({ idempotencyKey: "snapshot-job-123" });
console.log(snapshot.id, snapshot.sourceSandboxId);

await snapshot.delete();
await snapshot.delete(); // local no-op
```

`sandbox.snapshot(options)` returns `Promise<Snapshot>`. If
`idempotencyKey` is omitted, the SDK generates and reuses one for
transport retries; the same key against the same source sandbox returns
the same snapshot identity on idempotent replay.

Snapshot create requires a running source sandbox: a locally deleted or
observed-deleted sandbox throws `SandboxDeletedError`, a failed one throws
`SandboxFailedError`, a suspended one throws `SandboxSuspendedError`.

`snapshot.delete()` resolves to `void` and is idempotent on the same
object. A snapshot has its own identifier — you can delete it after
deleting the sandbox that produced it.

## Organizations

An API key belongs to a user, not a single organization, so one key works
across every organization that user belongs to. Calls are scoped to
whichever organization is current on the client.

```ts
const organizations = await client.listOrganizations();
for (const org of organizations) {
  console.log(org.id, org.name, org.personal, org.role);
}

client.organizationId = organizations[0].id;
```

`listOrganizations()` returns every organization the caller belongs to,
including their personal organization. `Organization.personal` marks that
one — it's the deterministic tenant an omitted organization context
resolves to, and every account has exactly one.

Assigning to `client.organizationId` changes which organization
subsequent calls run against, effective immediately. An empty value is
rejected as an `InvalidRequestError` rather than silently falling back to
the personal organization. To set it once at construction instead, pass
`organizationId` in the constructor options; reading
`client.organizationId` back returns whatever is currently in effect. See
[Configuration](/sdks/typescript/installation#configure) for the full
precedence and CI guidance.

## Error handling

All SDK exceptions inherit from `TytoError` (itself extending `Error`),
exposing `message`, `sandboxId`, `operationId`, `idempotencyKey`.

```ts
import { AuthenticationError, SandboxNotFoundError } from "@bonya-ai/tyto";

try {
  await client.getSandbox("sbx_123");
} catch (error) {
  if (error instanceof AuthenticationError) {
    console.log("check BONYA_API_KEY");
  } else if (error instanceof SandboxNotFoundError) {
    console.log("sandbox does not exist or is not visible");
  } else {
    throw error;
  }
}
```

| Error | Meaning |
|---|---|
| `AuthenticationError` | Invalid or rejected API key. |
| `InvalidRequestError` | Invalid local arguments or invalid service response. |
| `SandboxNotFoundError` | Sandbox missing, deleted, or not visible to the key. |
| `SandboxDeletedError` | Operation can't run — sandbox is deleted. |
| `SandboxSuspendedError` | Operation reported a suspended sandbox. |
| `SandboxBusyError` | Service rejected a lifecycle operation as busy. |
| `SandboxFailedError` | Operation can't run — sandbox failed. |
| `SandboxCreationFailedError` | Create reached a failed terminal state. |
| `SandboxCreationTimeoutError` | Create deadline expired. |
| `CapabilityRejectedError` | Guest capability rejected and couldn't be refreshed. |
| `SessionExistsError` | `createSession()` targeted a name with a non-replaceable record. |
| `SessionNotFoundError` | `attachSession()`/`killSession()` named a session that doesn't exist. |
| `JobRunNotFoundError` | `getJobRun()`/`cancelJobRun()` named a run that doesn't exist. |
| `JobScheduleNotFoundError` | A job schedule call named a schedule that doesn't exist. |
| `FilesystemError` | General filesystem failure. |
| `RemoteFileNotFoundError` | Remote file or directory missing. |
| `RemoteFileExistsError` | Remote destination already exists. |
| `CrossFilesystemMoveError` | Remote move crosses filesystems. |
| `FilesystemLimitError` | Client or service filesystem size/frame limit. |
| `ExecFailedError` | `ExecResult.check()` or `check: true` saw a non-ok result. |
| `TimeoutError` | Operation deadline expired. |
| `ConnectionError` | Retryable transport failure exhausted retries. |
| `ServiceError` | Service or unexpected transport failure not covered above. |

The SDK redacts API keys, capabilities, and selected operation identifiers
from mapped service error messages, and replaces path-like substrings with
`[redacted-path]`.

### Retries and idempotency

`maxRetries` (default `2`) controls SDK retries for retryable
control-plane operations. The SDK retries gRPC `UNAVAILABLE` for create,
get, list, delete, resume, snapshot create, and snapshot delete, while
preserving the same request and idempotency key where one exists. Exec
calls are not retried, except for one capability refresh when the SDK can
prove an exec capability token is expired before responses start.
Filesystem calls are not retried on transport unavailability; they may
refresh a rejected filesystem capability once.

Create and snapshot-create accept an idempotency key so a retried call
joins the original attempt instead of creating a second resource — see
[Idempotency](/concepts/idempotency) for what that key does and doesn't
protect against, and pass one explicitly whenever you might need to retry
a create across process restarts.

## Resource cleanup

There's no automatic cleanup on scope exit — use `try`/`finally`:

```ts
const client = new Tyto();
try {
  const sandbox = await client.createSandbox({ template: "bonya-dev" });
  try {
    const session = sandbox.execStream(["cat"]);
    try {
      session.write(new TextEncoder().encode("hello\n"));
      session.closeStdin();
      for await (const event of session) {
        // ...
      }
    } finally {
      session.close();
    }
  } finally {
    await sandbox.delete();
  }
} finally {
  client.close();
}
```

- `Tyto.close()` closes cached channels and is idempotent.
- `sandbox.delete()` affects the remote sandbox and updates the local
  handle to `Status.DELETED`; idempotent on the same object.
- Closing an unfinished `execStream()` session cancels the remote exec.
- Closing an unfinished `attachSession()` stream detaches the guest
  process rather than killing it — it keeps running.
- `snapshot.delete()` deletes the remote snapshot and is a local no-op
  when repeated.

For intentionally persistent sandboxes, don't delete on scope exit — store
`sandbox.id`, close the client, and reconnect later with
`client.getSandbox(id)`.

## Examples

Runnable programs ship in the SDK's `examples/` directory:

| File | Shows |
|---|---|
| `quickstart.ts` | Create, exec, clean up |
| `exec-streaming.ts` | Streaming output and stdin |
| `files.ts` | Read, write, upload, download, list |
| `sessions.ts` | Persistent terminals and replay |
| `previews.ts` | Publishing a port to a browser |
| `snapshots.ts` | Capturing sandbox state |

```bash
export BONYA_API_KEY=byk_...
npx tsx examples/quickstart.ts
```
